# OmniPost G1~G4 拟人化发布方案（产品文档 + 技术方案）

> 目标：把注入式平台（小红书/B站等）的发布从"DOM 直改"升级为"事件级拟人化操作"，配合 cookie 续期、指纹一致性、拟人化节奏，提升发布成功率。
> 时间：2026-08-29。前置文档：`发布成功率提升方案.md`（G 系列预估整体 +20~30%）。

---

## 〇、一句话结论

**G1 不引入 `chrome.debugger`**（会触发浏览器黄色"正在调试"警告条、attach 数量受限、干扰静默发布），而是**增强 content script 层的事件级拟人化**——真实键盘/鼠标事件 + 打字节奏 + 轨迹 + 随机延迟，达到同样的"拟人化"效果且零副作用。

---

## 一、现状技术画像（已核查代码，非推测）

| 项 | 现状 | 文件 |
|---|---|---|
| 注入式发布 | `ensureEditorTab` + `sendToTab` 消息 → content script 操作 DOM | `adapters/utils.ts` + `content/xiaohongshu.ts` |
| 文本注入 | `setNativeValue`（原生 setter + input/change 事件，React 可识别） | `content/lib/inject.ts:87` |
| 富文本注入 | `pasteIntoEditor`（ClipboardEvent paste，ProseMirror/Draft/Slate 均响应） | `inject.ts:116` |
| 发布点击 | `clickPublishAndConfirm`（点发布 + 处理确认弹窗） | `inject.ts:243` |
| 请求 | `apiFetch` 30s 超时 + AbortController，**无重试退避** | `adapters/api-client.ts:17` |
| 限速 | 固定 `sleep(3000)` 平台间隔 | `background/index.ts:613` |
| 权限 | 已有 `cookies`/`scripting`/`declarativeNetRequest`，**无 `debugger`** | `manifest.json` |
| 指纹 | 无主动管理（依赖浏览器原生环境） | — |

**关键判断**：现有注入已具备"事件级"基础（`setNativeValue`/`pasteIntoEditor` 都能被 SPA 框架识别），缺的是**「节奏」和「轨迹」**这两个拟人化关键特征——当前是"一次性瞬间塞入全文"，这正是风控最容易识别的机器特征。

## 二、G1：事件级拟人化输入层（核心）

### 2.1 为什么不引入 chrome.debugger

| 方案 | 拟人化程度 | 副作用 | 结论 |
|---|---|---|---|
| chrome.debugger + CDP | 高 | 浏览器顶部**黄色"正在调试"警告条**（无法隐藏）、attach 数量限制、页面事件被调试器占用、影响截图 | ❌ 不用 |
| content script 事件级拟人化 | 中高 | 无 | ✅ 采用 |

content script 运行在页面隔离世界，可以直接 `dispatchEvent` 真实的 `InputEvent`/`MouseEvent`/`KeyboardEvent`，React/ProseMirror/Slate 都能正确捕获——**效果等价于 CDP 输入，但无警告条**。

### 2.2 拟人化输入层设计（`content/lib/humanize.ts` 新增）

```
humanize.ts
├── humanType(el, text, { cps })     // 逐字/逐段输入，模拟真人打字
│     每次 dispatch InputEvent({inputType:'insertText', data: chunk})
│     配合随机 30~120ms 间隔，长文本分段（每 20~40 字停顿一次）
├── humanClick(el)                    // 先 mouseover→mousedown→mouseup→click，
│     带 80~200ms 随机间隔，模拟真实点击序列
├── humanScrollTo(el)                 // 平滑滚动到元素可视区再操作
├── humanDelay(min, max)              // 随机延迟
└── humanPath(from, to)               // 生成中间点，配合 dispatchMouseEvent 模拟轨迹
```

### 2.3 接入点

- `xiaohongshu.ts` / `bilibili.ts` 的 `XHS_INJECT_DRAFT` / `XHS_CONFIRM_PUBLISH` 改用 `humanType` + `humanClick` + `humanScrollTo`
- 标题用 `humanType`（短文本逐字），正文用 `humanType` 分段输入（长文本），发布用 `humanClick`
- 保留 `setNativeValue`/`pasteIntoEditor` 作为**降级回退**（若 humanType 抛错则回退旧方式，保证不因拟人化引入新失败）

### 2.4 关键边界

- **速度上限**：拟人化会变慢（打字逐字输入），正文太长时需提速——正文用"分段 paste"（每段 humanType 或 paste + 停顿），标题才逐字，避免发布耗时爆炸。
- **失败回退**：任何 humanize 函数失败都回退到 `setNativeValue`/`pasteIntoEditor`，**拟人化是增强不是替代**。

## 三、G2：cookie 复用 + session 续期

### 3.1 现实边界（必须说清）

**Cookie 的"续期"由平台服务端决定，客户端无法真正延长 cookie 有效期。** 我们能做的是：

1. **复用有效 cookie**（已有 `getCookie`，强化为批量读取 + 缓存）
2. **过期检测 + 预警**（`chrome.cookies.get` 读 `expirationDate`，计算剩余有效期）
3. **引导重登**（检测到过期/临期，跳登录页，登录完自动回到发布流）

### 3.2 实现

```
store / background
├── getCookieHealth(platformId)      // 读 cookie 剩余有效期，返回 { valid, remainingDays, expiresAt }
├── preflightLogin(platformIds)      // 发布前预检：扫描勾选平台，过期标红
└── sessionReauth(platformId)        // 过期 → 打开登录页 → 轮询检测登录恢复 → 继续
```

- `checkLogin` 现在"点一下查一次"，升级为 `getCookieHealth` 持续可查，popup 设置面板展示"剩余 X 天"健康看板。
- 发布管线开头插入 `preflightLogin`：勾选平台里有临期（<3 天）的，发布前弹提示；过期的直接跳过并标红。

### 3.3 边界

- 只对"cookie 登录态"平台有效（session 平台）；官方 API 平台（token）走 token 有效期检测。
- 无法突破平台的会话有效期限制，只能"提前发现 + 引导重登"。

## 四、G3：指纹一致性维护

### 4.1 核心原则：不破坏，不伪造

浏览器指纹（Canvas/WebGL/UA/字体/时区/语言）是**环境级**的，扩展应做到：

1. **不主动改变指纹**（不伪装 UA、不覆盖 navigator 属性、不注入会改变 Canvas 的脚本）
2. **请求头一致**（所有 `apiFetch` 用同一 UA/语言/时区，避免同一账号在不同请求间指纹漂移）
3. **固定环境复用**（同一账号始终在同一浏览器 profile 下操作，不跨 profile）

### 4.2 实现

- `api-client.ts` 统一请求头（Accept-Language 跟浏览器、Origin/Referer 走 declarativeNetRequest 已注入）
- 文档化"指纹三原则"写入代码注释，新增契约测试断言"不覆盖 navigator 属性"

### 4.3 边界

G3 是**防御性**的，收益在"长期稳定"（避免被风控判异常设备），短期单次发布无感。它的价值是让 G1/G4 的拟人化操作不因环境突变而被识破。

## 五、G4：拟人化节奏

### 5.1 现状

`background/index.ts` 里平台间隔是**固定 `sleep(3000)`**，这是"机器人固定节奏"特征。

### 5.2 实现

- `background` 平台间隔改 `humanDelay(2000, 5000)`（随机 2~5s）
- 发布管线每个阶段（checking→drafting→publishing）之间加随机微延迟
- 同一平台多账号/多篇连发时，额外加"错峰"随机间隔（避免整点定时发布被风控）

## 六、成功率预期（诚实声明）

| 手段 | 预估提升 | 落地后 |
|---|---|---|
| G1 事件级拟人化 | 注入式 +15~25% | 小红书/B站 45% → 65~70% |
| G2 cookie 续期/预检 | +5~10% | 减少过期导致的直接失败 |
| G3 指纹一致性 | +3~5% | 长期稳定性（短期无感） |
| G4 拟人化节奏 | +5~8% | 降低批量风控触发 |
| **合计** | **+20~30%** | 注入式平台整体 45% → 约 70% |

**重要声明**：
1. 以上是**估算模型**，不是实测。真实提升需用"发布成功/失败/原因"埋点数据跑一个月回校准。
2. 成功率有**硬天花板**：单账号 + 无协议号，注入式平台 70% 左右是合理上限，剩余是平台动态风控。
3. **无法"保证"固定百分比**——平台风控动态变化，今天 70%，平台改版可能回落。G1 的 value 是"把机器特征去掉"，让成功率逼近该平台人工发布的上限，而非创造不可能。

## 八、测试计划

- **单测**：humanize 各函数（humanType 逐字、humanClick 序列、humanDelay 范围、降级回退）
- **契约**：humanize.ts 存在 + 各 content script 接入 + 随机节奏 + cookie 健康函数
- **e2e**：真实 Chrome 验证注入式平台（小红书本地 mock 页）humanType/humanClick 真实触发 input/click 事件；随机延迟不破坏发布流
- **回归**：29 平台 checkLogin 全 false 防假成功红线不变

## 九、风险与回滚

- G1 拟人化会让注入**变慢**，正文太长需用"分段 paste"而非逐字，否则发布耗时不可接受。
- 所有 humanize 函数都有**降级回退**到旧 `setNativeValue`/`pasteIntoEditor`，任何异常不会引入新失败。
- 若某平台改版导致 humanize 定位失败，回退旧逻辑 + 上报错误，不影响整体。
