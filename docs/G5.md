# OmniPost G5 验证码打码方案

> 目标：当登录续期 / 发布环节触发人机校验时，自动识别并回填，减少"卡在验证码"导致的发布失败。
> 时间：2026-08-29。前置：`docs/G1G4.md`（G 系列），`发布成功率提升方案.md`。

---

## 〇、一个必须前置的诚实判断

**G5 对 OmniPost 的实际价值有限**，原因：

1. OmniPost 是"**复用已登录 cookie**"发布，不每次登录，所以**登录验证码场景少**。
2. 发布环节触发验证码，本质是**账号异常 / 风控升级**的信号——此时打码平台往往也救不了（滑块/点选需要真人行为，AI 识别率不高，且风控会持续拦截）。
3. 单账号个人创作者，验证码**频次极低**，成本几乎可忽略，但**收益也低**。

**结论**：G5 是"锦上添花"的可选项，优先级低。真正该做的是先把 G1~G4 实测跑通。若要做，**只做"图片字符验证码 OCR"这一种子类型**（成本最低、技术最稳），滑块/点选不做（性价比低）。

---

## 一、验证码类型与可打码性

| 类型 | 触发场景 | AI/人工识别率 | 建议 |
|---|---|---|---|
| **图片字符验证码**（4~6 位字母数字） | 登录、旧式表单 | 高（95%+） | ✅ 做，OCR 稳定 |
| 中文/算术验证码 | 少数国内站 | 中高 | ✅ 可做（国内打码平台强项） |
| **滑块验证码**（缺口拖动） | 登录、风控 | 中（需轨迹模拟，易被风控识别） | ❌ 不做，性价比低 |
| **点选验证码**（语序点击） | 高风控场景 | 低 | ❌ 不做 |
| **短信验证码** | 换设备登录 | 需接码平台（另一套，涉灰更深） | ❌ 不做 |

**G5 只做第一行「图片字符验证码 OCR」，其余留人工。**

## 二、打码平台选型（2026-08 核实）

### 国内（中文验证码强）

| 平台 | 计价 | 图片验证码成本 | 特点 |
|---|---|---|---|
| **超级鹰**（Chaojiying） | 题分制，1 元≈100 题分 | 约 0.002~0.03 元/次 | 中文/算术强，接口简单，国内主流 |
| **图鉴**（Rrocr） | 题分制 | 约 0.01 元/次 | 识别率高，API 稳定 |
| 云打码 / 斐斐 | 题分制 | 约 0.01 元/次 | 老牌 |

### 国际（现代验证码 / reCAPTCHA）

| 平台 | 计价 | 图片成本 | 特点 |
|---|---|---|---|
| **CapSolver** | AI，$0.4/1k 图片 | ≈0.0004 美元/次 | 快（5~15s），Cloudflare 支持好 |
| **CapMonster Cloud** | AI，$0.30~0.04/图片 | 低 | AI 识别 |
| 2Captcha / AntiCaptcha | 人工，$0.50/1k 图片 | ≈0.0005 美元/次 | 人工，慢（15~45s）但覆盖全 |

### 推荐

- **国内平台验证码** → 超级鹰（中文/算术强，题分制，充值门槛低）
- **若涉及海外站** → CapSolver（AI，快）

## 三、技术方案

### 3.1 架构

```
content script（各平台页）
  ├── detectCaptcha()：MutationObserver 监听验证码元素出现
  ├── captureCaptcha()：截取验证码 <img> 或 <canvas> → base64
  └── fillCaptcha(text)：输入识别结果 + 派发 input 事件（复用 G1 拟人化）

background（Service Worker）
  └── solveCaptcha(base64, type)：调打码平台 API → 返回识别文本
      · 国内：超级鹰 PostPic 接口（POST base64 图片）
      · 国际：CapSolver createTask/getTaskResult 轮询
```

### 3.2 关键流程

1. **检测**：发布/续期时，`waitForElement` 轮询验证码容器（`input[name*="captcha"]` 相邻的 `img`/`canvas`）
2. **截图**：canvas 用 `toDataURL()`，img 用 drawImage 到 canvas 再导出 base64
3. **打码**：background 调打码平台 API，带超时 + 失败重试（1 次）
4. **回填**：`humanType`（G1）输入识别结果，派发真实 input 事件
5. **校验**：输入后检测是否通过（验证码元素消失 / 出现成功提示）；失败 → 重新打码（最多 2 次）→ 仍失败则**暂停 + 通知用户人工处理**

### 3.3 平台 API 差异

- **超级鹰**：`http://upload.chaojiying.net/Upload/Processing.php`，POST 表单（user/pass/softid/codetype/len_min/file_base64），同步返回 `pic_str`
- **CapSolver**：`createTask`（POST JSON，type=ImageToTextTask）+ `getTaskResult` 轮询

> 两者都是纯 HTTP 请求，在 Service Worker 里 fetch 即可，**无新权限**（host_permissions 已含 http/https）。

### 3.4 配置（设置面板）

| 字段 | 说明 |
|---|---|
| 打码平台 | 超级鹰 / CapSolver / 关闭 |
| 平台账号/密钥 | 用户名 + 密码（或 API key） |
| 软件 ID | 超级鹰的 softid |
| 单次成本上限 | 超过则不自动打码（防意外扣费） |

> 密钥存 `chrome.storage.local`（本地，与 AI Key 同策略）。

## 四、成本估算（诚实）

| 场景 | 频次 | 单次成本 | 月成本 |
|---|---|---|---|
| 图片验证码（国内超级鹰） | 假设每月 20 次 | 0.01~0.03 元 | **< 1 元** |
| 图片验证码（国际 CapSolver） | 假设每月 20 次 | ≈0.0004 美元 | **≈ 0.06 元** |

**结论**：单账号场景下，G5 的金钱成本几乎为零；真正的成本是**开发时间 + 维护**（平台 API 变动、验证码类型升级）。这也是它优先级低的原因。

---

## 五、风险与边界（重要）

1. **触发验证码 = 账号异常信号**：打码只是"治标"，真正该做的是降低触发概率（G4 拟人化节奏已做）。
2. **滑块/点选不碰**：AI 识别率低 + 机器拖动轨迹易被风控识别，做了也是"假成功率"。
3. **短信验证码不碰**：需要接码平台，涉灰更深，与项目定位冲突。
4. **失败必须人工兜底**：打码失败 → 暂停 + 通知用户，绝不静默放弃（延续"防假成功"红线）。

## 六、实施建议

| 阶段 | 内容 | 是否做 |
|---|---|---|
| 现在 | 等 G1~G4 真实账号实测，观察是否真有验证码阻塞 | — |
| 若确需 | 只做「图片字符验证码 OCR」（超级鹰 + CapSolver） | 可选 |
| 不做 | 滑块 / 点选 / 短信 | ❌ |

**一句话**：G5 建议先不做，等 G1~G4 实测后，若真遇到"登录续期卡验证码"，再加「图片验证码 OCR」这一小块——它成本最低、技术最稳、够用。滑块/点选/短信明确不碰。
