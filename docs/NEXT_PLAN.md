# OmniPost 下一版本规划

> 结合市面同类产品（Wechatsync / MultiPost / 新榜 / 微小宝 / 新媒体管家）与当前可实现技术方案，聚焦「新颖实用」。
> 规划时间：2026-08-28。当前基线：29 平台一键发布 + 正文提取 + AI 生成 + 上传文档 + MCP/CLI。

---

## 一、现状与竞品定位

| 竞品 | 强项 | 我们的差距 |
|---|---|---|
| Wechatsync | 平台覆盖全、API 直发 | 已对齐平台数，但内容适配弱 |
| MultiPost | DOM 注入稳健 | 已对齐 |
| 新榜/微小宝 | 数据回流、选题热点 | **缺**（我们只发不回收） |
| 新媒体管家 | 多账号矩阵、定时 | **缺** |
| 通用 AI 写作 | 文案生成 | 已有基础版，但**无平台风格适配** |

**核心结论**：单纯"多发几个平台"已无差异化。下一版应转向 **「内容智能化 + 运营闭环」**——让用户在"写好 → 适配 → 排期 → 发布 → 复盘"全链路里少干活。

---

## 二、P0 —— AI 多平台风格自适应改写（核心差异化，必做）

**痛点**：一篇母稿发 29 个平台，知乎要深度、小红书要种草口吻+emoji、微博要精炼、X 要 280 字、Bluesky 要 300 字、公众号要排版。现在全平台发同一份正文，各平台都"水土不服"。

**方案**：AI 拿到「母稿 + 目标平台列表」→ 按平台风格 prompt 模板逐平台改写 → 每个平台发改写版。

- 平台风格库：每个 adapter 增加 `stylePrompt`（知乎=深度论述；小红书=口语化+emoji+话题标签；微博=140 字提炼；X=英文/双语 280 字；Bluesky=300 字素；公众号=标题党+排版）
- 复用现有 `ai-client.ts`，新增 `rewriteForPlatforms(motherDoc, platforms)` 一次调用批量产出
- 降级策略：某平台改写失败 → 自动回退母稿原文（不阻塞发布）

**可实现性**：✅ 高。完全基于现有 AI client + 纯 prompt 工程，零新依赖。成本约 1~2 天。

**价值**：这是「一次写、全平台各得其所」的杀手级能力，竞品普遍没有。

---

## 三、P1 —— 定时发布 + 发布队列（高频刚需）

**痛点**：内容要在最佳时段（早 8 点 / 晚 8 点 / 周末）发，现在只能手动。

**方案**：
- 待发布队列：`storage` 存 `scheduledQueue`（{ article, platformIds, scheduledAt }）
- `chrome.alarms`（已在用 bridge 轮询，复用机制）定时触发 → 到点走现有 `handleAutoPublishPipeline`
- Side Panel 新增「定时」按钮：选时间 → 入队 → 显示倒计时
- 失败重试：到点失败 → 标记 + 可重试

**可实现性**：✅ 高。MV3 alarms + storage 都是现成能力。成本约 1 天。

---

## 四、P2 —— 多账号矩阵（矩阵运营刚需）

**痛点**：矩阵号运营需要同平台多账号切换发布。

**方案**：
- `PlatformSettings` 从单账号改为 `{ accounts: [{ id, name, ...凭证 }], activeId }`
- 发布时选「账号」下拉；`checkLogin` / `createDraft` / `publish` 按 activeId 取对应凭证
- 平台卡片显示当前活跃账号名

**可实现性**：✅ 中高。需重构 store 的凭证结构（单值→数组），涉及 29 个 adapter 的取凭证逻辑（统一抽 `getActiveAccount(pid)`）。成本约 2~3 天。

---

## 五、P3 —— 内容素材库 + 模板（提效）

**痛点**：重复起稿、找不到历史内容。

**方案**：
- 发布历史升级为「内容库」：全文可检索、可复制、可"再次发布"
- 快捷模板：活动公告 / 产品测评 / 知识科普 / 观点短评 等结构化起稿模板
- 与 P0 联动：模板 → AI 扩写 → 平台适配 → 发布

**可实现性**：✅ 中。主要是前端 + storage 全文索引（29 平台历史数据量可控）。成本约 1~2 天。

---

## 六、P4 —— 数据回流（选做，受平台 API 限制）

**痛点**：发了不知道效果，无法复盘。

**方案**（分平台可行性）：
- 可做：Mastodon（公开 API 可查互动）、Bluesky（AT Protocol 可查 like/repost）、微信公众号（后台 API）、知乎（部分接口）
- 受限：小红书/微博/B站 等风控严格，只能"半自动"（用户授权后抓取，不稳定）

**建议**：先只做 Mastodon / Bluesky / 公众号 三个"数据开放"平台的阅读/互动回流，做成「发布后 24h 数据小结」。其余平台明示"暂不支持"。

**可实现性**：⚠️ 部分。成本高、平台间不统一，建议放到远期。

---

## 七、推荐路线图

| 版本 | 内容 | 价值 | 成本 | 状态 |
|---|---|---|---|---|
| **v0.2（下版）** | P0 AI 平台风格自适应 + P1 定时发布 | 差异化核心 + 刚需闭环 | 2~3 天 | ✅ **已完成** |
| **v0.3** | P2 多账号矩阵 + P3 内容库模板 | 矩阵运营 + 提效 | 3~5 天 | ✅ **已完成** |
| **v0.4（远期）** | P4 数据回流（开放平台）+ 更多海外平台 | 数据闭环 | 视情况 | 待规划 |

> 更新（2026-08-28）：P0~P3 已全部实现并通过测试（791 项契约 + e2e 23 项全绿）。详细设计见 docs/P0.md ~ P3.md。

**一句话建议**：下一版只做 **P0（AI 平台风格自适应）**，这是唯一能形成"人无我有"差异化的点，且成本最低、收益最大。P1 定时发布作为配套一起上。
