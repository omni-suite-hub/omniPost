# P1 — 定时发布 + 发布队列

> 版本：v0.2 P1。状态：设计定稿。
> 目标：内容在最佳时段自动发布，无需守着电脑。

---

## 1. 背景与问题

内容发布时间影响阅读量（早 8 点 / 晚 8 点 / 周末）。当前只能手动点发布，用户需要在特定时间守在电脑前。

---

## 2. 方案

**待发布队列 + 定时触发**：

```
popup「定时发布」→ 选时间 → 入队（storage 持久化）
        ↓
chrome.alarms 每 30s 轮询检查到期任务
        ↓
到期 → 走现有 handleAutoPublishPipeline（含 P0 AI 适配）
        ↓
发布完成 → 出队 + 写入发布历史
```

**失败重试**：到期发布失败 → 保留在队列并标记 `lastError`，Side Panel「定时队列」里可手动重试 / 移除。

---

## 3. 技术设计

### 3.1 队列存储（`store/index.ts`）

```ts
export interface ScheduledItem {
  id: string;              // 唯一 id
  article: Article;        // 待发布文章（含 title/body/media 元数据）
  platformIds: PlatformId[];
  scheduledAt: number;     // 目标时间戳（ms）
  aiRewrite: boolean;      // 是否 AI 适配（P0）
  createdAt: number;
  lastError?: string;      // 上次失败原因
}

// store 新增：
getScheduledQueue(): Promise<ScheduledItem[]>
saveScheduledQueue(items: ScheduledItem[]): Promise<void>
addScheduled(item: ScheduledItem): Promise<void>      // 追加
removeScheduled(id: string): Promise<void>            // 出队
```

### 3.2 定时触发（`background/index.ts`）

- 注册 `omnipost-scheduler` alarm（`periodInMinutes: 0.5`，与 bridge 轮询同机制）
- `chrome.alarms.onAlarm` 监听：名称匹配时执行 `runDueScheduled()`
- `runDueScheduled()`：读队列 → 过滤 `scheduledAt <= now` → 逐个 `handleAutoPublishPipeline(article, platformIds, aiRewrite)` → 成功出队+写历史，失败标 `lastError` 保留

### 3.3 消息

- `SCHEDULE_PUBLISH`：popup 入队（payload: { article, platformIds, scheduledAt, aiRewrite }）
- `GET_SCHEDULED`：popup 读取队列
- `REMOVE_SCHEDULED`：移除 / 重试（重试 = 移除原项 + 立即发布）

### 3.4 popup UI

底部操作条加「🕐 定时」按钮：
- 点击弹出时间选择（datetime-local 或快捷选项：1 小时后 / 明早 8 点 / 今晚 8 点）
- 确认 → `SCHEDULE_PUBLISH` → toast「已加入定时队列」
- 设置入口旁显示「定时队列」徽标（N 个待发）

---

## 4. 验收标准

1. 定时入队后，到点自动发布（无需打开 popup）
2. 队列持久化（重启浏览器不丢）
3. 发布失败保留队列并展示错误，可重试 / 移除
4. 支持 AI 适配（P0）联动
5. 到点发布复用现有管线（含登录态校验、防假成功）

---

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| SW 被回收，alarm 不触发 | MV3 alarms 由 Chrome 保证，SW 会被唤醒 |
| 到点时用户未登录某平台 | 复用 checkLogin，未登录平台标失败，其余照发 |
| 队列数据含 media dataUrl 超 storage 配额 | 复用现有"媒体仅存元数据"策略，发布时重新添加 |
