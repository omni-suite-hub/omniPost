# OmniPost 发布成功率提升方案

> 目标：在不碰协议号/账号买卖的前提下，把 29 平台一键发布的成功率从当前基线大幅拉高。
> 时间：2026-08-29。当前基线：29 平台（官方 API 7 个 / cookie+API 16 个 / 注入式 6 个）。

---

## 一、现状基线：当前成功率到底是多少

先把"成功率"拆到三类机制上，否则没法谈提升。以下是基于机制特征 + 行业经验的**估算基线**（非实测，落地后用真实发布数据回校准）。

| 机制 | 平台数 | 代表平台 | 基线成功率 | 主要失败源 |
|---|---|---|---|---|
| **官方 API + token** | 7 | Bluesky/Mastodon/WordPress/Telegram/Reddit/YouTube/Typecho/MetaWeblog | **90% ±5** | token 失效、限流 |
| **cookie + 平台内部 API** | ~16 | 知乎/掘金/微博/CSDN/百家号/公众号/语雀/思否/博客园/雪球等 | **65% ±10** | cookie 过期、接口签名/风控变动 |
| **注入编辑页（DOM）** | ~6 | 小红书/B站/豆瓣/X 等 | **45% ±15** | SPA 重渲染、验证码、页面改版、内容丢失 |

**加权基线（按均匀勾选平台估算）：约 66%**。

> 注意：这是"发出去且真的成功"的口径。当前已有"防假成功"红线（干净环境 29 平台 checkLogin 全 false），所以不存在假报成功，失败会明确报错——问题在于**失败率本身偏高**，尤其注入式平台。

---

## 二、提升手段分层（白区 + 浅灰区，明确不碰深灰）

### 分层原则

| 区 | 定义 | 风险 | 态度 |
|---|---|---|---|
| **白区** | 纯工程手段，完全合规 | 无 | 全部做 |
| **浅灰区** | 拟人化自动化、登录态复用，不完全符合平台 ToS 但无法律风险 | 低 | 可选做（用户已同意"稍微加灰"） |
| **深灰/黑** | 协议号、账号买卖、批量注册、绕实名、大规模矩阵 IP 对抗 | 高（法律/封号） | **不碰** |

---

### 白区手段（零风险，先做）

| 序号 | 手段 | 作用 | 预期提升 |
|---|---|---|---|
| B1 | **登录态预检 + 过期预警** | 发布前先扫勾选平台，cookie 过期的提前标红，避免发到一半才失败；加"登录态健康看板"显示剩余有效期 | +8~12% |
| B2 | **草稿兜底强化** | 已有"先建草稿再发布"，补上：发布失败时草稿明确保留并可一键重试（而不是只报错） | +3~5% |
| B3 | **发布后回读校验** | 发完主动回读一次，确认内容真实存在，只信"回读通过"而非 API 返回的"成功" | +3~5% |
| B4 | **分段重试 + 指数退避** | 网络抖动/限流时自动重试 2~3 次（3s→9s→27s），临时性失败自愈 | +5~8% |
| B5 | **session 一键重登** | 登录态失效的平台，点一下跳登录页，登录完自动回到发布流继续 | 配合 B1 |

**白区合计：+15~20%（66% → 约 80%）**

---

### 浅灰区手段（低风险，可选）

| 序号 | 手段 | 作用 | 预期提升 | 灰色说明 |
|---|---|---|---|---|
| G1 | **CDP 拟人化操作** | 注入式平台（小红书/B站）改用 CDP 模拟真人点击/输入，而非 `executeScript` 直接改 DOM（SPA 检测不到直改会丢内容） | 注入式平台 +15~25% | 模拟真人操作，浅灰 |
| G2 | **cookie 复用 + session 续期** | 复用现有登录态，配合平台刷新接口自动续期，减少过期 | +5~10% | 登录态复用，浅灰 |
| G3 | **指纹一致性维护** | 保持同一浏览器环境稳定指纹，避免被风控判"异常设备" | +3~5% | 稳定性优化，浅灰 |
| G4 | **拟人化节奏** | 批量发布加随机延迟、模拟滚动/鼠标轨迹，降低"机器人批量操作"风控触发 | +5~8% | 拟人化，浅灰 |
| G5 | **验证码打码平台**（可选） | 检测到人机校验时，接入第三方打码平台自动识别（有成本，按次计费） | +5~10% | 中灰，需额外成本 |
| G6 | 住宅代理 IP | 仅多账号矩阵场景需要，单账号用不上 | — | 中灰，暂不做 |

**浅灰区合计（单账号，不含 G5/G6）：+20~30%**

## 三、成功率量化分析：大概能提高多少

### 分阶段预估

| 阶段 | 落地手段 | 整体成功率 | 说明 |
|---|---|---|---|
| **当前基线** | — | **~66%** | 三类机制加权 |
| **白区完成后** | B1~B5 | **~80%** | 消灭 cookie 过期 + 假成功 + 临时失败 |
| **白区 + 浅灰完成后** | B1~B5 + G1~G4 | **~87%** | 注入式平台从 45% 拉到 70%+ |
| **再加打码平台** | + G5 | **~90%** | 有按次成本，可选 |

### 分平台机制预估（白区+浅灰全做后）

| 机制 | 基线 | 目标 | 提升 | 主要功臣 |
|---|---|---|---|---|
| 官方 API | 90% | **95%+** | +5% | B3 回读校验 + B4 重试 |
| cookie + API | 65% | **82~85%** | +18~20% | B1 预检 + B4 重试 + G2 续期 |
| 注入式 | 45% | **72~78%** | +28~33% | G1 CDP 拟人化 + G4 节奏 + B2 草稿兜底 |

### 结论（一句话）

> **从 ~66% 提升到 ~87%**，即整体成功率提升约 **20 个百分点**（相对提升 ~32%）。若再上打码平台可到 ~90%。**90% 左右是单账号、无协议号场景的合理天花板**——剩下的 10% 是平台动态风控导致的，无法靠纯技术消除，只能靠"失败留草稿 + 人工接管"兜底。

### 诚实声明

1. 以上百分比是**基于机制特征和行业数据的估算模型**，不是实测值。落地后需用真实发布数据（成功/失败/原因）回校准，形成 OmniPost 自己的成功率基线。
2. 成功率有**硬天花板**：单账号 + 无协议号，90% 是上限。想再往上，要么碰协议号（不碰），要么改半自动确认模式（对标 social-push，成功率≈100% 但需人工点确认）。
3. 平台风控是**动态的**——今天 87%，明天某平台改接口可能回落到 80%。所以 G1 的 CDP 适配需要持续维护（这也是商用 SaaS 团队的价值所在）。

## 四、实施优先级路线

### 阶段一：白区（先做，零风险，最大 ROI）

1. **B1 登录态预检 + 健康看板** —— 发布前扫 cookie，过期标红；设置面板加各平台剩余有效期展示
2. **B4 分段重试 + 指数退避** —— 发布管线加重试（3s→9s→27s）
3. **B3 发布后回读校验** —— 发完回读确认（各平台"成功"语义不同，需逐个定义回读方式）
4. **B2 草稿兜底强化** —— 失败明确保留草稿 + 一键重试入口

### 阶段二：浅灰（可选，按需）

5. **G1 CDP 拟人化** —— 复用现有 e2e CDP harness，替换小红书/B站等注入式平台的 DOM 直改
6. **G4 拟人化节奏** —— 随机延迟 + 轨迹
7. **G2 session 续期** —— 各平台刷新接口接入
8. **G5 打码平台**（最后，有成本才上）

### 阶段三：数据校准

9. 埋点记录每次发布的「平台/机制/成功/失败原因/耗时」，跑一个月形成**真实成功率基线**，回校准本文档的估算值，再决定是否追加投入。

## 五、风险与边界（重要）

- **明确不碰**：协议号、账号买卖、批量注册、绕过实名认证、大规模矩阵 + IP 对抗风控——这些有法律/封号风险，且与 OmniPost"本地免费、个人创作者"的定位冲突。
- **浅灰区风险提示**：G1~G4 虽无法律风险，但仍是"不完全符合平台 ToS"的自动化行为，极端情况下平台可能限制登录或要求验证。建议**控制发布频率**（配合 G4 拟人化节奏），避免短时间高频发布触发风控。
- **成功率提升 ≠ 零人工**：即便到 90%，仍有约 10% 需要"失败留草稿 + 人工接管"兜底。这是诚实的边界，不是缺陷。
